# AI Client Tools and Capabilities

**Audience:** Users integrating an AI client or operating supported MCP tools. This is a detailed capability reference for the currently integrated source tree, not proof that each optional runtime is installed on a particular host or present in an older Stable release.

## How an AI client discovers and uses this Agent

The MCP server provides **concise routing instructions** for the persistent workspace, choosing between Git/worktree, worker shell/jobs, workspace files, optional LSP/DAP, PTY and Browser/E2E tools, and preserving critical approval and access boundaries. Per-tool descriptions, argument schemas and safety annotations carry the detailed usage limits, capability requirements and warnings; optional runtimes must be checked before use. Compatible clients can discover these capabilities without a separately pasted global prompt, but what each client passes to its AI model or can render remains client-dependent. Neither instructions nor MCP hints grant additional permissions or override repository-specific rules.

## Client and vendor neutrality

MCP is the current primary common client boundary; it is not OpenAI-specific. ChatGPT is the current supported/validated client path and keeps dedicated setup documentation below.

Future AI/MCP clients may be supported through bounded client-specific integration/authentication paths, but they must reuse the same Agent tools, executor, policy, approval and lifecycle semantics. A provider-specific UI, credential, tunnel or confirmation mechanism must not become a core safety dependency.

Support for another commercial AI client is claimed only after its current protocol/auth/tool behavior has been verified and accepted; this architecture does not imply universal compatibility.

After upgrading an Agent, a connected client may retain stale tool descriptions even while the Agent binary and tool names are current. ### Optional multi-language code and debugger readiness

The first Stable slice of Issue #140 includes only tested, bounded supported modes. Language servers and debuggers are optional administrator-owned runtimes; the core installer does **not** install Node, PHP, Python, Rust, their language adapters, database tools or Chromium automatically. MCP discovery of a tool does not mean the selected runtime is installed. Pass an exact worker workspace, `file_version` and explicit SQL dialect. A successful `debug_adapter_status` **tool call** can correctly report `status=unavailable`.

| --- | --- | --- |

| PHP | pinned Phpactor with no Composer/project execution | CLI `.php` Xdebug/DBGp-to-DAP; additional *local PHP HTTP Service Job* request mode, with independently owned Service, root-owned private DBGp socket, one explicit request and adapter-only detach (requires an installed release containing the mode, trusted optional adapters and an authorized Service Job) |

The offline SQL migration supplement (when available in the installed release) recognizes dbmate-style paired `-- migrate:up` / `-- migrate:down` sections (including repeated pairs and `transaction:true|false` directives). Only forward `Up` SQL can supply a table/view or column outline or a version-pinned reference/definition; rollback SQL is ignored while original source offsets remain unchanged. Unsupported/malformed directives (including near-markers missing the required separator after `--`), mixed runner annotations and ambiguous statement boundaries fail closed. MySQL/MariaDB `DELIMITER` mode and unsupported stored-program/compound bodies **even without DELIMITER** are rejected consistently by both source-outline and navigation: nested procedural SQL is not treated as top-level schema, including when a migration contains dbmate annotations. Plain `BEGIN;` and `BEGIN WORK;` transactions are not rejected merely for their transaction marker. Executable MySQL `/*!...*/` and MariaDB `/*M!...*/` comments in forward SQL are also rejected after Up/Down normalization, because they can change statement grammar; ordinary comments, quoted strings and rollback-only executable comments remain supported. PostgreSQL source navigation also recognizes bounded `CREATE MATERIALIZED VIEW ... AS` (direct `SELECT`/`WITH`/`TABLE`/`VALUES`, optionally with a simple column list), `DROP MATERIALIZED VIEW` and `REFRESH MATERIALIZED VIEW` forms. Only an actual source declaration can justify type-specific refresh/drop navigation in either direction; unsupported storage headers, malformed population suffixes, conflicting relation kinds and ambiguous history do not become assumed live schema. Identity-changing `ALTER MATERIALIZED VIEW ... RENAME TO` and `... SET SCHEMA` invalidate older definitions in ordered migration history, whereas valid `RENAME [COLUMN] old TO new` preserves the relation's identity. Conflicting typed DROP operations fail closed, and unknown ALTER identity changes cannot preserve obsolete CREATE state. A synthetic new-schema lifecycle marker is never offered as a selectable SQL reference. This is a conservative boundary, not a MySQL procedure parser or a general SQL grammar. This does not run dbmate, execute SQL, query database state or automatically install SQL adapters. Verify the installed release contains the capability; current `main` source support alone never proves deployment.

**SELECT/JOIN column navigation (when included in the installed build):** For an explicit `sql_dialect` of PostgreSQL, MySQL or MariaDB, the existing `code_definition` and `code_references` resolve a qualified column token in a bounded, ordinary `SELECT ... FROM table [AS] alias [JOIN table alias (ON ... | USING (col [, ...]))]` to its actual table-column declaration in version-pinned SQL migration files. For example, `a.id` in `SELECT a.id FROM accounts AS a` resolves `accounts.id`; aliased source names cannot also be used as unaliased table names. Only a proven single query scope is eligible (max eight source tables). The same bounded SELECT scope produces both table-level and column-level references; unsupported FROM/JOIN/ON grammar yields neither kind of offline navigation, including a cursor on a PostgreSQL `ONLY` modifier. Physical relation names across other offline DDL/DML, REFERENCES and index paths use one dialect-aware relation-name guard; bare DDL column identifiers have a separate context-sensitive keyword check. Unqualified `SELECT id`, CTEs/subqueries, PostgreSQL table column-alias lists that positionally rename columns, implicit comma/NATURAL/LATERAL/CROSS joins, invalid or ambiguous USING lists, missing/empty `JOIN ... ON` predicates, set operations, ambiguous aliases, unconsumed FROM/JOIN tokens, PostgreSQL unquoted reserved/type-function keywords at table-source or alias positions (for example, the `ONLY` inheritance modifier), stored procedures and unsupported shapes stay with SQLLens or return no invented offline target. Quoted PostgreSQL identifiers such as `"only"` remain valid names; bare `ONLY` remains a permitted MySQL/MariaDB table name, and qualified names following a dot retain their dialect rules. A strictly parsed `JOIN ... USING (col [, ...])` list admits only 1–64 unique, dialect-legal single column names (quoted or bare; MySQL/MariaDB ASCII column deduplication is case-insensitive even across quotes, ambiguous Unicode is rejected; PostgreSQL quoted case remains distinct); unqualified USING members are not mapped to one physical table, while independently qualified `a.id`/`p.id` uses remain navigable. The `ON` validator recognizes only simple complete comparisons, numeric operands, `IS [NOT] NULL/TRUE/FALSE`, `LIKE`/`ILIKE`, `AND`/`OR`/`NOT` and bounded parentheses; contradictory JOIN modifiers, reserved bare SQL words posing as ON identifier operands or unsupported syntax fail closed. Supported boolean/NULL literal operands and dialect-legal quoted/post-dot identifiers remain valid. The offline tokenizer omits literal values but preserves their presence to fail closed for elided strings within consumed table names, qualification separators, `AS`/alias tokens and `ON` (including before a clause boundary or statement end); unrecognized tokens after table bindings are not ignored. A qualified function-call identifier such as `a.id()` is not a column reference, while an independent real `a.id` in the same SELECT remains navigable. Search/document versions, DROP/RENAME lifecycle history and strict bounded results remain enforced. PostgreSQL reserved/type-function keywords at the *leading* columnref identifier (`ONLY.id`, `TABLE.id`) invalidate physical column navigation; legal post-dot attributes (`a.select`) and quoted leading identifiers are preserved. Direct CREATE VIEW/MATERIALIZED VIEW/TABLE AS SELECT and INSERT INTO ... SELECT dependencies only come from a wholly validated bounded SELECT body, never generic non-SELECT FROM/JOIN token scanning; unsupported/ambiguous embedded references are omitted. Supported parenthesized CREATE TABLE definitions have statement-level preflight so one illegal unquoted column, REFERENCES target or simple constraint-key member cannot leave its table/earlier columns as source declarations. Multi-action ALTER TABLE also rejects all column occurrences when a supported column action has an invalid bare identifier; migration rename ambiguity remains fail-closed. Before emitting physical navigation, a complete bounded statement proof is required for CREATE TABLE field/constraint syntax, all ALTER TABLE action segments and CREATE INDEX key lists/suffixes. Structurally invalid bare datatype keywords and incomplete DEFAULT operands cannot make CREATE TABLE declarations, while complete signed/numeric or separately elided string defaults remain supported. Literal-elision gaps within consumed qualified SELECT columns invalidate the source scope; the same bounded SELECT projection and supported WHERE/ORDER/GROUP/LIMIT/OFFSET clauses are checked for standalone and embedded SQL. An unconsumed second projection alias or extra visible expression tokens cannot publish physical source identity; separately projected string literals and ordinary qualified function calls remain supported. CREATE AS view/table declarations require positively proven query bodies, not merely an AS header; valid but unsupported CTE, VALUES, TABLE, table-function and complex query bodies conservatively yield no physical navigation, although independent document-symbol outlines may still recognize them. This is a conservative grammar subset, not proof that arbitrary DDL is executable. No SQL is executed, no database is contacted, and no direct ChatGPT presentation or installed-version support is implied by source acceptance.


**Bash Shell DAP (included in immutable Stable v0.1.19; installed-client acceptance is separate):** Call `workspace_stat` for the exact workspace-relative `.sh`/`.bash` script, then `debug_launch(language="shell", mode="bash", workspace=..., program=..., file_version=..., stop_on_entry=true|false)`. Register up to 32 version-pinned breakpoints **in that original script** with `debug_breakpoints`, then invoke `debug_configure` to begin execution. Read `debug_status`, `debug_threads`, `debug_stack`, `debug_scopes`, `debug_variables`; use `debug_continue`, `debug_next`, `debug_step_in`, `debug_step_out` and always `debug_stop` for verified cleanup. Bash DEBUG-trap breakpoints remain *unverified until actually hit*: a line number alone does not prove that Bash will execute a command there. Only the original script, its own Bash process, bounded variable snapshot and a current top-level command frame are supported. This executes the selected workspace script **as the existing worker identity** and is not a passive check. The original root-owned Agent binary is also the minimal Go DAP adapter, launched in the existing executor-owned private cgroup with a root-trusted `/usr/bin/bash` interpreter; a private worker-side, safe-open `workspace_read` snapshot captures and seals at most 1 MiB of the file under the requested `file_version` *before* Bash is started. The original Bash PID waits in a fixed non-user bootstrap until Executor identity/cgroup/source proof is complete, then execs Bash against the **inherited sealed source fd**, never reopens the pathname, and installs the sealed `BASH_ENV` DEBUG hook. **The original root broker**, not the unprivileged adapter, provisions the inherited 0600 root-owned command and event pipes; the kernel must also enforce **Yama `ptrace_scope >= 1`** to block `pidfd_getfd` duplication by unrelated same-UID peers. If that sysctl is unavailable or 0, Shell DAP reports unavailable and refuses to launch/configure; it never changes the host setting. DAP reports the original source path and lines; Bash itself sees `/proc/self/fd/6` as the script path, so scripts relying on `$0` or `BASH_SOURCE` as their own workspace filename are not transparently supported. No Node.js, bashdb, mkfifo, global `pkill`, exposed socket, or adapter reverse terminal request is introduced. Arbitrary `debug_evaluate`, asynchronous `debug_pause`, non-Bash POSIX semantics, sourced-file/subshell stepping, remote/root/extension-host attach and transparent debugging of scripts that replace the DEBUG trap are **not supported**. If source snapshot/version verification, original binary/Bash chain, pin/cgroup membership or cleanup cannot be verified, the operation fails closed. A failed post-spawn configuration or uncertain START is not retryable within the same Session; use `debug_status` and `debug_stop` to reconcile the original cgroup. Source acceptance is not installed or client acceptance.

**Single-target UPDATE/DELETE column navigation (when included in the installed build):** For PostgreSQL/MySQL/MariaDB, `code_definition` and `code_references` also resolve proven `UPDATE table SET column=value WHERE column=...` and `DELETE FROM table WHERE column=...` source column uses across version-pinned migration files, including simple matching target-qualified WHERE references. Only complete single-table statements are eligible: no aliases, UPDATE FROM, DELETE USING, CTE, JOIN, RETURNING or live database inference. Literal/boolean/default scalars are not physical columns; unknown qualifiers and incomplete/unsupported syntax cannot manufacture migration links. Normal source-version/search/migration lifecycle, reply-size and worker authorization guards are unchanged.

JS/TS VS Code extension-host debugging is Owner-deferred to future work, not an active release requirement. ### Structured worker workspace editing

`workspace_stat`, `workspace_read`, `workspace_write`, `workspace_apply_edits`, `workspace_transfer`, and `workspace_search` in `text` mode use a separate worker-credential helper. This is **not** a general sandbox for worker shell access: `run_command` and intentional worker tools retain their documented Linux authority. The helper uses descriptor-relative `openat2` access and a per-request Landlock filesystem boundary; it fails closed with `workspace_sandbox_unavailable` when the kernel does not expose Landlock ABI v2 or when a container disables it. This kernel capability is not present in every stock Ubuntu 22.04 or Debian 11 installation; Agent core/platform support does not imply these optional structured worker tools are available on that kernel. Text search also needs a trusted `/usr/bin/rg` binary, but the core installer does not automatically install it.

For unfamiliar or large source files, `workspace_stat` reports size and file version without reading any file bytes; it does not detect MIME type or interpret binary/media. Use a small explicit `workspace_read` range with a matching `file_version` instead of the up-to-1 MiB default. This separates byte limits from model context budgets. Ordinary project reads/writes remain limited to a chosen workspace and regular files, and never automatically stage or commit Git changes. Existing privileged `read_file` / `write_file` retain **root-host-file** authority and are not silently rewritten into worker operations. Batch edits require explicit version/must-not-exist preconditions, validate every path and replacement before the first mutation, and report per-file outcomes when later writes race or fail. The helper request is bounded by the same 8 MiB wire budget as the executor; JSON escaping is counted before pre-action audit and helper launch, and oversized serialized batches return a deterministic `input_too_large` rather than `unknown_completion`. They do not silently discard unrelated changes or claim filesystem-wide atomicity. LSP WorkspaceEdit and future structural rewrite application must reuse this same edit/precondition layer rather than introduce a second writer.

### Resumable worker-side file ingress (Issue #99 Rev 3)

`workspace_transfer` implements a single direct-mode Agent contract: `begin` with a stable 16–128-character ASCII `transfer_key`, exact workspace/relative path, total bytes, full SHA-256 and exactly one destination precondition (`must_not_exist` or `file_version`); `chunk` with base64 bytes up to 256 KiB, exact raw `offset` and per-chunk SHA-256; `status` with durable `next_offset`, `prepared_bytes` and expiry; `commit` with **bounded, durable 4 MiB preparation windows** followed by whole-object SHA-256 validation and atomic final publish; and `abort` for any state not already publishing. A successful `commit` may return `status=preparing` (not yet published): call `commit` again with the same `transfer_id` until `status=committed`. Completed windows and SHA-256 continuation survive helper crash/restart and are not recopied on retry. Retry identical begin with the same key after a lost response; the handle embeds a material fingerprint and a partial begin retains its key/material reservation through startup/periodic GC for its configured TTL. A different-material retry is rejected until that reservation expires; an identical retry reclaims only an empty, manifest-less partial begin. An existing-file replacement uses a durable displaced-inode metadata snapshot and persists exchange verification before deleting the displaced original. After a recoverable post-exchange race, `status=conflicted` means **not committed** and the concurrent destination was restored; `commit` returns `file_changed` rather than republishing. Uncertain commits are reconciled by `status` or same-handle retry; incomplete prepared bytes never appear as a completed destination. The same worker-only openat2/Landlock confinement applies, extended solely to its private `state_dir/worker-home/transfers` staging area. This is a scoped structured-tool boundary, **not** isolation from separately authorized worker shell access sharing the `aiworker` Unix identity.

Operators can tune `runtime.transfer_staging_mib` (default 512; 16–1048576), `runtime.transfer_active_sessions` (default 8; 1–64), and `runtime.transfer_session_ttl_seconds` (default 3600; 60–86400). These are cumulative staging, active-session and retention budgets; they do not raise global MCP/IPC request limits or confer root authority. The running Executor launches a bounded worker-only Landlock cleanup at startup and every minute, regardless of new client traffic; expiration also sweeps on new begin. Retained bytes in aborted/committed records remain quota-accounted until unlink, and status/abort/commit retry terminal cleanup. The receipt namespace itself has a bounded 4096-entry admission budget and automatically frees expired entries; a full namespace returns an actionable resource error. Physical expiry can be delayed if Executor is stopped or cleanup is blocked by unsafe state, which is reported rather than silently deleting unproven user data. Prepared destination temporary files may require up to one additional whole-object allocation on the destination filesystem; each 4 MiB preparation window checks disk headroom. Secure preparation requires Linux unnamed destination-inode creation (`O_TMPFILE`) plus successful post-journal linking; unsupported destination filesystems or link restrictions fail closed with `transfer_prepare_unavailable`/`transfer_prepare_link_failed`, not unsafe deletion or root fallback. An unlinked temp inode is automatically reclaimed on helper death, while every named temp must match an earlier fsynced inode journal before cleanup. Ambiguous publication fails closed for explicit reconciliation. Version-pinned outgoing content still uses `workspace_stat` and bounded `workspace_read` windows, including binary base64 encoding. Neither an uploaded byte stream nor `structuredContent` proves that a particular ChatGPT client supports attachments, native typed files, or unlimited model-visible text. Issue #99/#59 retain those direct-client acceptance gates.

### Ordinary commands and root commands

Use `run_command` for normal development work, builds, tests, Git, project package managers and diagnostics that do not require host privilege. It runs as `aiworker` with the configured workspace root as default CWD; HOME/XDG are shared Agent-private worker state, separate from each worktree. Synchronous `run_command` / `run_root_command` calls use the administrator-configured `command_timeout_seconds` (default 300 seconds; validated range 10–1800 seconds); the effective value is advertised to the model in both tool descriptions. Work expected to exceed the configured limit or produce high output should use `start_job`. Command bodies are limited to 256 KiB and are delivered to Bash through stdin rather than being copied into the spawned process argv. Synchronous stdout/stderr is captured with a 1 MiB production-time head/tail bound and returns explicit encoding, raw-byte, truncation and duration/timeout metadata; binary output is base64-encoded instead of being treated as UTF-8. Active synchronous worker and root execution have separate bounded capacity and fail immediately with a structured `busy/resource_limit` result instead of entering a hidden queue. Cancellation/timeout terminates the command process group with TERM followed by a bounded KILL fallback, and ordinary same-process-group background children are cleaned up; a command that deliberately escapes that process group cannot be claimed as stopped, so durable/background work belongs in `start_job` or an intentionally managed service.

`/srv/ai-workspace` is persistent. Connected models are instructed to inspect and reuse existing repositories, worktrees and task environments before creating duplicates, prefer `git worktree` when another checkout of the same repository is appropriate, and never treat dirty, untracked, ambiguous or unknown workspace state as safe to delete.

### Code search: text, structural and semantic

Use the lowest inspection layer that answers the question correctly: `workspace_search mode=text` for ordinary bounded literal/regex text occurrences, `workspace_search mode=structural` for AST/syntax-tree shapes, and LSP for symbol/type/reference meaning. Advanced or unstructured `rg`/`git grep` through `run_command` remains the intentional CLI escape hatch, with ordinary `aiworker` authority rather than the structured helper's Landlock sandbox. Structured text mode requires a trusted `/usr/bin/rg` and available Landlock ABI >=2; if either is missing, it fails closed instead of silently changing authority. Both search modes return bounded results with workspace-relative files, zero-based ranges and explicit partial/truncation metadata; the structural mode also returns bounded metavariable captures.

The first-class structural path is read-only. It never exposes ast-grep rewrite/apply flags, never creates a code index, uses one scan thread, rejects requested search paths that resolve outside the selected workspace, does not enable ast-grep `--follow`, and runs ast-grep with `--config /dev/null` so repository `sgconfig.yml`/advanced rule configuration is not implicitly loaded. Advanced ast-grep rules/codemods remain an intentional direct-CLI escape hatch rather than an expanded MCP surface; any future first-class structural edit must flow through the safe workspace-edit/precondition semantics tracked separately instead of making ast-grep a second filesystem writer.

The Agent detects a trusted full `ast-grep` executable and requires version 0.40.5 or newer for the current JSON-stream contract. Linux `/usr/bin/sg` is not treated as ast-grep because that name is commonly owned by util-linux. Structural search does not silently install tooling: if no trusted compatible engine is present, it fails clearly so installation/provisioning can remain an explicit lifecycle action.

### Repository environment discovery

`repository_environment` takes an explicit repository/worktree path inside the configured workspace and returns a bounded structured summary of repository-owned development intent. It recognizes common native manifests/lockfiles and toolchain pins plus declared mise, devenv, Dev Container and Dagger mechanisms, reports repository-owned setup/test/build entrypoint identities where they are explicitly declared without returning package-script bodies, and compares required tools/versions with compatible host/system or worker-cache executables. Git-tracked declarations are distinguished from both untracked state and tracked-but-uncommitted changes so server-local state does not silently become durable project truth.

Discovery is descriptive only. It does not install packages/toolchains, execute repository tasks/scripts, choose a hidden precedence between conflicting environment/package-manager declarations, or create an Agent-owned environment database/provider abstraction. Multiple declared mechanisms or conflicting pins return explicit selection/conflict state. Agent-managed capability tools such as tmux/LSP/DAP/ast-grep/Playwright remain a separate ownership class from repository dependencies. Declaration content is read with worker authority. System-tool version probes run only for trusted root-owned, non-writable system executables; probes are bounded and run as the worker outside the project checkout. Worker-cache candidates are not executed merely for discovery; a recognizable cache path may supply a version hint, but compatibility remains unknown until a later intentional execution/verification path proves it. Trusted system Go `version` probes run with Go telemetry disabled **only inside a disposable, worker-owned probe HOME**, and probe cleanup failures are reported instead of silently ignored. This does not change the worker's real `go telemetry` configuration or enable Go module/toolchain downloads. For trusted system-tool version probes, structured `tools[].reason` uses the bounded code `version_probe_failed` for an ordinary probe failure, `version_probe_cleanup_failed` for cleanup failure alone, or `version_probe_and_cleanup_failed` when both fail. Each has compatibility `unknown`; the response never includes raw temporary paths, subprocess output or cleanup-error text. Both underlying internal Go errors remain available for diagnosis. Repository declaration paths that escape through symlinks are ignored.
### Repository and worktree lifecycle

The structured repository tools solve checkout **identity and lifecycle correctness**; they do not replace Git. `repository_discover` finds bounded Git identities under the configured workspace and can filter by canonical remote identity without contacting the remote. `repository_inspect` reports the exact repository/worktree path, common Git directory, HEAD, branch or detached state, upstream divergence, staged/unstaged/untracked/conflict counts, in-progress Git operations, remotes and linked worktrees. Optional `verify_remote=true` checks either an explicitly selected configured remote/branch or the current upstream with `git ls-remote` without fetching or moving local refs; this is the structured reconciliation step after an ordinary CLI push. Credential-bearing URL userinfo/query data is not returned.

`worktree_create` requires an exact expected start SHA and refuses stale refs, a branch already checked out elsewhere, path collisions and ambiguous state. `worktree_remove` never removes the main worktree or local branch, never uses force, and refuses dirty/untracked/conflicted/in-progress or incompletely inspected state. Normal removal additionally proves that the selected external remote branch is exactly at the expected HEAD; `disposable=true` is an explicit escape hatch only for a clean task worktree whose external durability is intentionally not required.

Ordinary `git status`, `git diff`, `git log`, `git fetch`, `git commit`, `git push` and similar verbs remain normal Git CLI through `run_command` or future PTY use. Structured lifecycle Git runs under `aiworker`, stays inside the configured workspace (including Git/common metadata), disables repository hooks/external fsmonitor integration, refuses repository checkout filters on the structured create path, and uses non-interactive Git arguments rather than shell-composed path/ref commands. Repositories that intentionally require checkout filters remain usable through ordinary Git CLI.

Use `run_root_command` only when host-level privilege is genuinely required. Normal root commands can execute directly, but commands that reference protected Agent resources, can interrupt connectivity/control-plane services, or match destructive-operation policy return `approval_required` first. The connected client/model should explain the exact risk and retry with `approval=true` only after explicit user confirmation.

This is a safety guardrail, not a claim that arbitrary root shell access is mathematically incapable of causing damage. Root remains powerful; the design combines AI-visible self-preservation instructions, server-enforced approval policy, minimal/sanitized root execution environment, audit logging and explicit human gates for known high-risk categories.

### Self-preservation manifest

Before host-wide package, service, firewall, network, disk, user, web-stack or control-panel changes, connected clients/models are instructed to call `agent_environment` and preserve the critical resources it reports.

The manifest identifies, among other things:

- `ai-server-agent.service` and `ai-server-agent-executor.service`;
- `/usr/local/bin/ai-server-agent`;
- `/etc/ai-server-agent`;
- `/var/lib/ai-server-agent`;
- `/var/log/ai-server-agent`;
- the private executor Unix socket under `/run/ai-server-agent/`;
- the configured MCP listen endpoint/port;
- required host primitives such as Bash, systemd and `systemd-run`;
- read-only capacity for the filesystem backing the configured workspace, including an advisory warning when available space is below 2 GiB or 10%; filesystem telemetry never performs cleanup and a telemetry read failure does not make `agent_environment` fail.
- a non-secret random `instance_id` (`asa_` plus 128 random bits) in the root-managed Agent config, included in authenticated `agent_environment` and `/agent-environment.json`. Normal update, repair, reinstall, credential rotation, hostname/IP changes and state-preserving VM copies retain the same ID; explicit purge and fresh installation generate a new one. A state-preserving VM copy retains the existing Agent instance ID; changing its hostname or IP does not generate a new identity.

The executor separately protects Agent names/paths/socket/listen address and known connection-risk/destructive command patterns. The intent is that ChatGPT both **knows what must survive** and is **server-side gated** when a command directly threatens those resources.

### File I/O and downloads

`read_file` and `write_file` operate on host paths through the Agent. Ordinary project files can also be created/read through `run_command` as `aiworker` inside `/srv/ai-workspace`.

These MCP file tools are intentionally privileged host-file operations, not an unprivileged workspace filesystem. A caller allowed to use `read_file` may reach root-readable sensitive files; `write_file` can produce root-equivalent host changes. Agent protected-resource approval is defense-in-depth and does not classify every sensitive path on the host.

`read_file` is a bounded regular-file ranged read. It accepts raw-byte `offset`/`limit` values (maximum 1 MiB per call), returns `next_offset`, `file_size`, `file_version`, `eof`, byte/truncation metadata and explicit `utf-8` or `base64` encoding, and never loads an arbitrary whole file before applying the limit. A caller assembling several ranges should send the previous `file_version`; replacement/truncation/modification fails with `file_changed` instead of silently stitching different generations together. Kernel/control pseudo-filesystems and non-regular targets such as FIFOs, sockets and devices are not treated as ordinary files.

`write_file` remains a bounded complete replacement for ordinary source/config/text files (maximum 1 MiB). The destination parent must already exist. The executor resolves the parent through a held directory descriptor, rejects final symlinks/special nodes, writes and fsyncs a private temporary file, and preserves existing ownership and mode unless an explicit mode is supplied. Existing files may use the prior `file_version` as an optimistic precondition; those writes use an atomic exchange so the exact destination displaced at commit time can be identity-checked against the validated object. If another object won the pathname race, the executor restores that displaced object only when rollback identity can be proven and returns `file_changed`; any uncertain committed/final state returns `unknown_completion` rather than false success. New-file workflows use `must_not_exist` with `RENAME_NOREPLACE`. Ordinary success is returned only when the final pathname is verified to name the prepared replacement before and after parent-directory fsync.

Protected-resource approval is evaluated against both the requested path and the safely resolved effective path, so a normal symlinked parent/alias cannot turn an Agent-protected target into an unprotected spelling. Unsafe or ambiguous file types fail closed; broad arbitrary host access remains available only through the explicitly privileged shell boundary.

The host can download project dependencies or public files through ordinary command-line tools such as `curl` when the project needs them. Agent credentials/config/state remain protected and must not be copied into chat, source control or public logs.

The MCP file tools are content/path based; they are **not a generic automatic synchronization layer for arbitrary ChatGPT UI attachments**. If a workflow needs a user attachment transferred to/from the VPS, use an explicit supported transfer path and validate that path for the specific client/runtime instead of assuming attachment sync from `read_file`/`write_file` alone.

### Persistent jobs

Use `start_job` for commands that should continue if ChatGPT disconnects or the MCP request ends. The Agent uses transient systemd units and stores job state under the root-controlled Agent state directory. Non-root jobs run as `aiworker`; root jobs go through the same approval policy before starting.

Persistent execution is fail-fast and bounded: by default six tasks and three independent services may run concurrently (each configurable 1..64), there is no hidden queue, each job retains at most 8 MiB of stdout/stderr in a bounded on-disk ring, and the newest 32 terminal job artifact sets are retained. `job_output` uses logical byte offsets and reports the earliest retained offset when older bytes have rolled out; binary chunks are returned as base64. Before accepting new disk-growing job work the executor also requires a state-filesystem safety reserve derived from configured/still-active task/service counts plus retained artifacts (using hard bounds only when trusted inventory is unavailable), so even abnormal retained jobs remain inside the modeled disk envelope.

`start_job` accepts an optional caller-generated `operation_id`. Retrying the same material request with the same key returns the original job handle; reusing that key for different command/root material fails with `idempotency_conflict`. The durable idempotency/recovery record contains a keyed fingerprint rather than the shell body. Every job gets a bounded internal recovery claim even when the caller does not supply `operation_id`; the caller key only adds replay identity. The protected shell body itself is handed to a fixed `job-runner` entrypoint through a normally short-lived protected job file rather than `bash -c <command>` argv. The runner scrubs the command contents as soon as it has safely consumed them (and on definitive setup failures where it can); privileged terminal reconciliation retires any leftover handoff before reporting a terminal result. A worker-writable status marker never overrides authoritative systemd active/pending state. If the executor dies in the pre-launch window, later job admission retires stale handoffs after the executor's broad connection deadline when no runner/unit evidence exists.

`start_job` also participates in the global lifecycle lock: admission through launch holds a shared lock, while install/update/uninstall/purge use the exclusive lifecycle lock. That makes destructive lifecycle removal mutually exclusive with a new persistent-job launch instead of relying on a racy one-time active-job check. Safe uninstall and purge still refuse to proceed while any `ai-job-*.service` unit is active. Stop the jobs first, then retry the lifecycle action.

### Browser capability

Browser automation is optional and installed on demand. The core MCP service does not depend on system Node.js or Chromium.

`browser_status` reports bounded, non-secret readiness and the desired/installed Node, Playwright and Chromium build identity. In installed builds supporting Browser concurrency, it also returns aggregate `browser_active`, `browser_limit`, `shared_profile_reserved` and `isolated_slots_available` with no session identity disclosure. The shared profile stays exclusive; the separate `browser_concurrent_slots` default is 2, configurable 1–64 for concurrent isolated sessions and runs, additionally subject to existing worker/process budgets. Maintenance is globally exclusive and never runs over an admitted Browser. These capabilities were published starting with immutable Stable `v0.1.21`; use a compatible installed Agent/Executor and verify the optional Browser runtime on the actual host. Neither a merged PR nor publication alone upgrades an occupied Agent. `browser_setup` requires explicit approval because it downloads a private runtime and may install Chromium system libraries. Setup is bounded to twenty minutes, runs one-at-a-time without a hidden queue, holds the global Agent lifecycle lock while changing the private runtime/host packages, and converges `/opt/ai-server-agent/browser` to an Agent-pinned manifest rather than treating an existing Node binary as proof that the runtime is current. Node downloads are SHA-256 pinned for supported architectures, Playwright dependencies are installed from the repository-embedded exact `package-lock.json` with registry integrity metadata, and the expected Playwright/Chromium/FFmpeg versions plus architecture-specific SHA-256 content-tree digests are verified before a staged runtime replaces the old engine. Transient setup directories/caches are cleaned separately from persistent browser state. If setup is interrupted after moving the previous engine aside, the next setup restores the single known backup before doing new work; multiple ambiguous backups fail closed for operator reconciliation.

`browser_run` uses **server-side headless Chromium**, not the user's personal desktop browser. Scripts are limited to 128 KiB, handed to the worker-side browser process through the already bounded executor stdin path and a per-run temporary file rather than process argv, and execute with a 90-second default / five-minute maximum timeout. Combined output uses the same bounded structured UTF-8/base64 executor result contract as synchronous commands. Managed Browser execution is fail-fast but **not globally one-at-a-time**: the shared profile remains exclusive, while independent isolated profiles can run concurrently within the configured Browser budget (default 2, 1–64). Each one-shot run additionally consumes Worker command capacity, and cross-call sessions additionally consume shared stdio-session capacity. Setup/maintenance excludes all managed Browser activity. The Executor must prove the entire Browser-owned process cgroup empty (including detached Chromium process groups) before releasing admission or reclaiming a profile. Saturation returns `resource_limit` instead of queueing. HTTPS certificate validation is enabled by default. `ignore_https_errors=true` is an explicit request-scoped exception for local/self-signed development and does not change the default for later runs.

### Playwright CLI compatibility and E2E acceptance

The existing private Playwright runtime also bundles the compact agent-oriented `playwright cli` command (snapshot/element refs, interaction, console, network and tracing). It can be exercised by an unprivileged `run_command` without installing another npm package or browser. Unlike `browser_run`, the CLI maintains its own browser process and session across CLI invocations; **do not assume the two share a page or cookies**. A bare CLI open defaults to system Google Chrome, which can be absent. An explicit CLI configuration must select Chromium with the verified pinned engine executable; set `PLAYWRIGHT_BROWSERS_PATH` to the installed private engine's browsers directory. Keep CLI HOME/XDG, snapshots, traces and downloads in a worker-owned private location **outside Git worktrees**, then close the session.

The reproducible opt-in compatibility test is `AI_SERVER_AGENT_BROWSER_CLI_ACCEPTANCE=1 bash tests/browser_cli_acceptance.sh`. Run it only on an authorized development/test host where `browser_status.ready=true`. The test uses a synthetic, local DOM with a private disposable CLI session and does not install tooling, contact a website or touch the Agent-wide browser profile. It proves only the pinned CLI consumer path. Direct CLI daemon sessions do **not yet** participate in managed Browser concurrency admission, lifecycle or disk-retention controls; do not treat this compatibility proof as an approved replacement for the managed Browser/E2E capability (#63), real installed-client acceptance (#59) or typed screenshot/trace delivery (#99).

### Managed Browser/E2E flows

`browser_e2e` runs up to **12 ordered steps in one bounded managed Chromium execution**. A minimal form test uses a `steps` array like:

```json
[
  {"action":"goto","url":"http://127.0.0.1:8080/"},
  {"action":"snapshot"},
  {"action":"fill","role":"textbox","name":"Email","value":"test@example.invalid"},
  {"action":"click","role":"button","name":"Submit"},
  {"action":"assert_text","selector":"#result","expected":"Saved"},
  {"action":"console"},
  {"action":"network"}
]
```

The `goto` URL above is **illustrative**, not a service started by Agent. Element operations accept **either** a CSS `selector`, an accessible `role` plus exact `name`, or a snapshot-issued `ref` for `click`, `fill` and `assert_text` within the **same call**. A complete, stable accessibility snapshot may return a bounded `refs` list (e.g. `e1`, `e2`) with `refs_scope=flow_only`, accessibility `role` and within-role `role_index`, and `refs_dropped`. Refs never carry raw DOM `tag`, `name`, `title` or `placeholder` hints. They are issued only when an independently verified second accessibility snapshot matches, the role/order headers are unambiguous, each staged handle is **re-resolved after final snapshot verification and compared by exact DOM identity**, and a document/root mutation guard remains stable; unprovable snapshots return no refs with `refs_unavailable=true` and an actionable `refs_reason`. This intentionally fails closed for shadow DOM scopes and inaccessible/inert controls rather than guessing. Refs identify the originally selected DOM element; they do not silently retarget replacement nodes. Invalid/expired refs fail safely, and navigation discards previous refs. Text assertions poll within a bounded step timeout; failures identify the step and stop subsequent actions. An accessible snapshot is capped at 8192 UTF-8 bytes and explicitly marks truncation (overly large DOM trees are rejected before snapshot creation, and a narrower CSS/role scope can be supplied); a shared output budget of 12000 bytes bounds returned snapshots and events. Console/network event counts are bounded, and network URLs omit query/fragment values. Every flow shares the existing `browser_run` profile, TLS behavior, fail-fast admission, executor time/resource budgets and temporary-file cleanup. **The steps and their element refs share one live page only within the call**; this is not a persistent cross-call browser session or a reusable CLI element-ref handle. For authenticated cross-call refs use `browser_session_open` and `browser_session_flow` (`refs_scope=session_until_invalidated`); direct detached CLI sessions do not inherit managed Browser lifecycle limits. Binary trace/screenshot delivery remains under Issue #99; flow step timings are not a Playwright trace ZIP. The old `browser_run` JavaScript escape hatch remains unchanged. For an oversized JPEG from the **same** managed Browser session, call `browser_session_image` with `{"operation":"capture","workspace":"/absolute/worktree","session_id":"<session>","quality":70,"max_width":1024,"max_height":720}`. Copy `file_version` and `file_size` from the result; `{"operation":"read","workspace":"/absolute/worktree","session_id":"<session>","file_version":"sha256:<digest>","offset":0,"limit":2048}` returns one bounded Base64 chunk. Continue at the exact returned `next_offset` until `eof=true`, reconstruct and verify SHA-256 in the consuming client, then `{"operation":"discard","workspace":"/absolute/worktree","session_id":"<session>","file_version":"sha256:<digest>"}` or close the Browser. Capture replaces any previous staged image (old versions become stale); a failed capture does not preserve stale image bytes. The JPEG is only in the ephemeral Browser process and cannot be assumed to render inline in ChatGPT; native attachment presentation remains separate (#99). An older installed build will not expose this tool.

For a private trace first open `browser_session_open` with `profile_mode="isolated"`, then use `browser_session_trace` for record, bounded read windows and discard. Shared/default sessions return `browser_trace_requires_isolated_profile`. Isolated managed Browser sessions run as separate `aibrowser` without worker-worktree file access; workspace remains an authorization binding. For opt-in Chromium kernel sandbox hardening, open with `{"workspace":"/absolute/worktree","profile_mode":"isolated","chromium_sandbox":true}`. This requires compatible user namespaces, seccomp and (where enforced) AppArmor policy and a real root-owned Executor cgroup. It is **off by default** pending broader supported-host compatibility evidence; sandbox-on on a shared profile is rejected. An explicit request must either return `chromium_sandbox=verified_at_start` or a typed failure (`browser_sandbox_unavailable` for startup or `browser_sandbox_unverified` for missing renderer/kernel proof), never a silent no-sandbox retry. Errors may include `cleanup_unverified` with a same-principal session ID; reconcile using `browser_session_close` rather than assuming admission was released. This hardening is not a distinct Linux UID per authenticated principal, and remains conditional on the actual installed release, pinned Browser runtime and kernel policy. Publication alone neither upgrades a host nor proves its Chromium sandbox compatibility.

The persistent browser profile is intentionally **Agent-wide shared state**. It is not isolated per connected MCP client or authenticated principal: any authorized browser caller may act through cookies, local-storage and session state left by another authorized browser caller. Durable profile state is preserved across runs/setup. Per-run downloads/temp files and ordinary relative artifacts are confined to a disposable working directory capped at 256 MiB, known Chromium caches are explicitly size-limited/cleaned, and browser execution maintains a 512 MiB state-filesystem safety reserve without deleting the durable profile. Browser scripts still have ordinary worker filesystem authority for explicitly chosen absolute paths; `browser_run` is not a filesystem sandbox. Setup requires a 2 GiB engine-filesystem reserve so the staged verified runtime can coexist safely with the previous runtime and download/package overhead.
